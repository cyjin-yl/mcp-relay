## Production Go prerequisite completed

The new server supplies authenticated caller identity and expiry outside tool
arguments, enforces write scope for workspace lifecycle, and pushes owner
revocation to workspace-capable device sockets even after a tool call has ended.
It is needed before workspace-capable clients are promoted.

The server-only transaction completed at 10:03:21 UTC. It used the existing
release lock, compared the old installed and running executable, checked the
stable manifest and current proxy configuration, retained a verified rollback
copy, atomically installed the frozen executable and restarted only the server.
An isolated transaction exercise covered both success and rollback after a
controlled health failure.

Independent production observation verified:

- The installed and running executable both match
  `ea5f15a5919c140eea9f893e20c71aa6e8a0e549da79da0e87039d242a1c4e88`.
- `healthz` and `readyz` both returned HTTP 200.
- The old Linux 0.1.7 client and Android 0.1.11 client reconnected naturally.
  A unique challenge was returned by an actual authenticated Linux device call
  through the new production server.
- The original Linux worker remained alive. A concurrent independent background
  build also remained alive. No persistent kernel was reset and no device worker
  was signalled.
- The stable client manifest remained at 0.1.11. Its SHA-256 before and after was
  `c0db783fed7ace5596e4de260a9dab37ca4d0349e9e7e6e5c3412c7f85a03c21`.
- No proxy configuration, production database schema, device configuration or
  Windows lease was changed by this transaction. No rollback was needed.

The original read-only runtime collector and the original authenticated callback
validator were used without modification. Original connector results, the
challenge, server start time, disk/running hashes and the collector hash are
retained in the private operational evidence.

Successful reconnect and callback do not establish that all device queues are
idle. Short shell requests also encountered queue timeouts during this work;
longer-budget finite calls completed. That scheduling observation is separate
from server health and artifact acceptance.

### Exact-binary owner and revoke blackbox

An additional test launched the exact deployed server executable on loopback
with a new private database. Only synthetic user, device and share fixtures
existed there. Authentication passed through the actual HTTP handlers, and the
synthetic device registered through an authenticated WebSocket.

Eight checks passed:

1. The running test executable matched the deployed binary, and a private owner
   session authenticated.
2. A synthetic device authenticated and registered over the real WebSocket path.
3. The trusted caller owner and expiry overrode forged values in tool arguments.
4. Distinct shares produced distinct workspace owners.
5. A read-only share could not call `computer_session`, even when the device
   misleadingly advertised a read-only annotation.
6. Revoking a share after its HTTP tool call had completed delivered the matching
   `workspace_revoke` frame to the idle device connection.
7. The revoked token failed while another share owner continued to work.
8. All synthetic shares were revoked, the test process exited and its disposable
   database was removed.

The final blackbox harness SHA-256 is
`beb6c4b66761de417c83ae8e721386fdbcfaf780b5354bec266ee5989c7f8353`.
The run completed at 10:11:57 UTC. It did not create or revoke production shares,
operate a native desktop, or touch existing user leases. This evidence is kept
distinct from the live production callback and from Windows native acceptance.

## Remaining release gates and continuation

The Windows target was offline during this continuation. Its existing operator
fence remains active. Historical deployment invocations were neither re-armed
nor replayed.

Before stable client promotion and npm publication:

1. Complete the native Windows sign-in flow documented in
   [windows-workspace.md](windows-workspace.md). The receipt must match the final
   runtime and harness, and demonstrate capture/input, unchanged physical input
   state, PointerGuard and visible application-preserving recovery after owner
   loss. Failed automatic sign-in and fail-closed cleanup are not this proof.
2. Reconcile the actual Windows task/process inventory, active operator and
   deferred writers. Preserve current device identity, configuration reference,
   root and update settings. The authorized managed invocation must retain all
   existing effective packs and include `computer`; a version update alone
   does not enable that pack.
3. Refresh the release plan against the current production baseline. The proxy
   configuration had independently changed before this server-only transaction.
   Its reviewed current SHA-256 was
   `1abcc5190010e4526cc800c5c5e3741992c9b06612030ade336df8efbf136753`.
   The historical frozen promotion wrapper still pins the earlier proxy hash.
   Reconcile and bind a new reviewed plan rather than overwriting the current
   proxy or weakening its compare-and-swap check.
4. Refresh the original runtime/callback evidence and continuation observations
   immediately before final promotion. Run the combined artifact gates, promote
   the immutable client and manifest once, publish the verified npm tarball,
   and verify the managed Windows worker and advertised Computer Use tools after
   reconnection.

These steps retain the combined release boundary. Unit tests, a prepared package,
source CI or the completed Go prerequisite do not waive Windows native acceptance.
