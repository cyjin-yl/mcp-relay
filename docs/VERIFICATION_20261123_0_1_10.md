## Why this release is needed

The Android 14 device exposed two concrete compatibility defects.

### Package Manager stdin option boundary

The first structured setup diagnostic reached the install phase and reported exit 255, `unsupported_install_option`, and `mayHaveApplied=true`. A subsequent read-only package check confirmed that the relay input bridge was absent. The device's Package Manager help and the Android 14 source identify the cause: a bare `-` is consumed by option parsing unless `--` first ends that scan.

The fix sends `pm install -r --user <current-user> -S <APK-size> -- -`. It retains the same signed, embedded APK bytes, current Android user, privileged channel, watchdog and integrity checks. It does not relax installation permissions or retry an uncertain operation automatically.

The regression includes a negative control for the old arguments and a positive check of the actual quoted arguments, exact APK bytes, size, current user and one-install idempotence. The terminator-only source passed typechecking and all 31 Android tests before the rotation defect below was found; that intermediate result is not the final release gate.

Sources:

- [Android API 34 BasicShellCommandHandler](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/+/88c7ff1cd72d6305ec59f97aadc2198cc2dc3592/android-34/com/android/modules/utils/BasicShellCommandHandler.java)
- [Android 14 PackageManagerShellCommand](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/services/core/java/com/android/server/pm/PackageManagerShellCommand.java)

### Effective default-display geometry

A read-only observation on Android device `localhost-0a22` at 2026-11-23 21:57:38 UTC produced this independent evidence:

| Source | Width × height | Rotation / orientation |
| --- | --- | --- |
| Physical size and default base DisplayInfo | 1840 × 2944 | 0 |
| Default override DisplayInfo | 2944 × 1840 | 1 |
| Default DisplayFrames | 2944 × 1840 | 1 |
| Default input viewport, logical and physical frames | 2944 × 1840 | 1 |
| Native PNG IHDR | 2944 × 1840 | Not encoded in IHDR |

The old parser returned the first base DisplayInfo. That made screenshot pixels use incorrect independent axis scales of 1.6 and 0.625. The input viewport and current window geometry establish that those scales were incorrect on this device; the conclusion does not rely only on the PNG aspect ratio.

Android's own [LogicalDisplay implementation](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/services/core/java/com/android/server/display/LogicalDisplay.java) applies Window Manager's override width, height and rotation to its base metadata. The repair must select verified current geometry for the default display and reject conflicting or unscoped information.

The original Android harness derives its input from native view bounds using the same scale that the backend inversely applies. Those calculations cancel, so that harness alone cannot verify the screenshot-pixel mapping. Independent screenshot-pixel acceptance is a separate release/device gate.

### Scroll contract correction

Review of the intended real MCP scroll call exposed a separate API mismatch. The shared `computer_action` schema bounds `scroll.amount` to 1–40 steps, as used by the desktop backends. The Android backend instead interpreted an explicit amount as pixels, while its omitted-amount default was 400 pixels. The source-level Android harness used 350 directly at the backend boundary, which would not satisfy the real MCP schema.

The repair in source commit `6b55ebeb044feea250e99b363463a9303010dd0f` accepts 1–40 integer steps, defaults to 3, converts each step to 120 screenshot pixels and bounds the swipe to 75% of the active screenshot axis before the existing native-coordinate conversion. The manual harness now requests 3 steps through the same public contract. Regression cases cover the default, explicit steps, scale conversion, large-request bounds and rejection before native input. The v1 artifact directory, all 219-test/31-native evidence and failed/partial Android receipts remain intact as history. No v1 promotion plan was created or executed.
